# Backend платформы прогнозирования пассажиропотока — требования v2

> Историческая спецификация требований. Текущее состояние реализации и проверки — в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) и [VALIDATION.md](VALIDATION.md).

## Основание и статус

Документ обновляет ранее согласованную архитектуру Python/FastAPI на основании двух предоставленных отчётов:

- **D** — `DATASET_DESCRIPTION.md`, подробный анализ от 25 сентября 2026 года.
- **S** — `Сводка_по_данным.txt`, сводные результаты по labels и первым 5000 строкам сырых CSV.

Статистические значения ниже приведены по отчётам, а не получены повторным чтением исходного dataset в рамках этого обновления. Ссылки вида `[D, §6]` обозначают раздел источника. Новые требования и архитектурные решения являются проектными предложениями.

Backend: Python. Java и Spring не используются. Сценарии, сравнение сценариев, самостоятельный режим очередей, времени ожидания и риска не уехать не входят в текущий объём.

## 1. Основной продукт и пределы подтверждённой детализации

**BND-01.** Основной показатель — `successful_validations`: число строк с `validation_result = 1` по публичному номеру маршрута, календарной дате и часу `tran_date_time`. Имя `boardings` сохраняется как имя поля предоставленных labels, но в API и интерфейсе его смысл описывается как успешные валидации, а не все фактические посадки. [D, §1, §4, §6]

**BND-02.** Базовая числовая детализация — `route × local_date × hour`. Направление, остановка, перегон и вагон не являются наблюдаемыми измерениями этой целевой величины. [D, §1, §10]

**BND-03.** Непосредственно реализуются прогноз по маршрутам, агрегация по времени и маршрутам, историческое сравнение, графики, карта справочной сети, временная навигация, приём/воспроизведение событий и экспорт.

**BND-04.** Число людей на остановке в момент времени, фактические посадки, выходы, наполнение салона, проценты вместимости и остановочные прогнозы не публикуются как доступные числовые показатели на основании одного маршрутного target.

**BND-05.** Для отсутствующей детализации API сообщает `METRIC_GRAIN_UNAVAILABLE`. Сервис не распределяет маршрутную сумму по остановкам произвольными долями и не выдаёт результат за обученный остановочный прогноз.

**BND-06.** Географическое ограничение может обрезать отображаемую линию. Оно не превращает маршрутную сумму в пассажиропоток выбранного участка. Это различие отражается в контракте ответа.

**BND-07.** Непокрытые исходными данными требования задания фиксируются в README как ограничения и условия подключения дополнительных данных, а не объявляются выполненными.

## 2. Канонические периоды и маршруты

**SET-01.** Целевой реестр строится независимо от наличия положительных labels и географии. Фиксированный конкурсный набор: `{1, 5, 7, 11, 12, 17, 25, 26, 28, 50}`. [D, §9]

**SET-02.** Обучающая история по правилам: 01.01–31.08.2025. Доступный отложенный период: 01.09–31.10.2025. Финальный скрытый период: 01.11–31.12.2025. После выбора подхода допускается обучение на январе–октябре. [D, §2]

**SET-03.** Внутренние интервалы полуоткрытые: история `[2025-01-01 00:00, 2025-11-01 00:00)`, конкурсный прогноз `[2025-11-01 00:00, 2026-01-01 00:00)`.

**SET-04.** Исходные timestamp не содержат часовой пояс. Предлагаемый контракт импорта — трактовать их как местное время `Europe/Moscow`; это допущение должно быть явно записано в конфигурации и манифесте. Нельзя сначала объявлять их UTC и автоматически сдвигать календарные часы. [D, §4]

**SET-05.** Историческая сетка содержит `10 × 304 × 24 = 72 960` ключей, финальная — `10 × 61 × 24 = 14 640`. [D, §6]

**SET-06.** Маршрут №5 сохраняется во всех реестрах и финальном результате. Нулевой прогноз — только явная политика `zero_fallback_no_positive_history`, а не доказательство отсутствия будущего движения или спроса. [D, §7]

## 3. Импорт и нормализация

### 3.1. Два режима подготовки

**IMP-01. `prepare-labels`.** Быстрый рабочий путь: чтение labels, проверка схемы и ключей, создание полной сетки, сохранение канонических маршрутно-часовых значений. На старте API исходные CSV не перечитываются.

**IMP-02. `audit-raw`.** Отдельная команда читает оба сырых CSV порциями или через columnar-инструмент с ограничением памяти, воспроизводит target, составляет отчёт и строит дополнительные исторические признаки. Повторный полный аудит не требуется для каждого HTTP-запроса или перезапуска.

**IMP-03.** Labels и агрегаты raw — два представления одной величины. Они сравниваются, а не суммируются.

### 3.2. Правила сырых событий

**IMP-04.** CSV: `;`, UTF-8, 14 исходных полей. Разбор задаётся явной схемой. Идентификаторы сохраняются без потери строкового представления. [D, §4]

**IMP-05.** Для target используются только `ngpt_route`, `tran_date_time`, `validation_result`. Фильтр — строго `validation_result = 1`; дополнительный фильтр по `tran_type_id = 52` запрещён. Отказы не считаются посадками и не интерпретируются как доказанная неоплата проехавшего пассажира.

**IMP-06.** Время target — только `tran_date_time`. Аномальные служебные даты отмечаются флагами качества; это не основание удалять корректную успешную валидацию из target.

**IMP-07.** Сначала объединяются источники, затем выполняются агрегация по времени события и разбиение по календарным границам. Файл не определяет период принадлежности события.

**IMP-08.** 523 успешные сентябрьские операции из `train.csv` уже включены в `labels_day_test.csv`. Их нельзя потерять при raw-агрегации и нельзя повторно прибавить при использовании labels. [D, §6]

**IMP-09.** Ноябрьский хвост `test.csv` — 615 операций, из них 562 успешные — сохраняется отдельно как пограничные исходные данные, но исключается из истории прогноза, выпущенного на начало 1 ноября. Эти записи не дают полного факта ноября. [D, §6]

**IMP-10.** `place_id` — площадка/депо, не остановка. `pass_route` не считается точной траекторией; `device_no` не равен вагону, количество устройств не равно выпуску; `bus_exit_no` не является подтверждённым ID фактического рейса. [D, §4, §9]

**IMP-11.** У `good_type` очищаются внешние пробелы с сохранением исходного значения. Неизвестные коды не получают выдуманной расшифровки.

### 3.3. Идемпотентность без потери target

**IMP-12.** `tran_no` и `(device_no, tran_no)` не используются как уникальный ключ события. В отчёте отмечены повторяющиеся значения обоих вариантов. [D, §5]

**IMP-13.** Для импорта файла идентичность записи — `(file_content_hash, logical_record_index)`. Повторная обработка того же файла не добавляет его заново. Другой файл с похожими записями не удаляется автоматически по совпадению номера карты/транзакции.

**IMP-14.** Для эмулятора идентичность доставки — `(source_id, run_id, batch_id)` либо подтверждённый источником идентификатор события. Транспортный дубль отделяется от похожих реальных операций.

**IMP-15.** Одинаковый ключ доставки с другим содержимым — конфликт, а не молчаливая замена. Если источник не предоставляет устойчивую идентичность, ограничение гарантий явно документируется.

## 4. Полная сетка, нули и качество

**GRID-01.** Отсутствующие ключи дополняются нулём для официального target в пределах проверенного исторического окна. Это отсутствие успешных операций в выгрузке, а не доказанное отсутствие пассажиров или полнота источника. [D, §6]

**GRID-02.** История включает 57 551 положительный ключ и 15 409 добавленных нулевых; 7 296 нулей относятся к №5. За пределами исторического окна значение не дополняется фиктивным нулём.

**GRID-03.** Для каждой точки сохраняются `value_origin` (`label`, `raw_aggregate`, `filled_zero`), `coverage_status`, признаки аномалии и необязательные количества всех/неуспешных операций. Если сырые признаки не рассчитывались, они имеют `null`, а не 0.

**GRID-04.** Маршрут №5 имеет поддержку `no_positive_history`. Наличие одной неуспешной операции 29 октября не создаёт положительный обучающий target. [D, §7]

**GRID-05.** Падение по №50 20–21 сентября отмечается как требующее проверки. Ноль 21 сентября и 304 успешные операции 20 сентября не интерполируются в официальной разметке. Причина не считается установленной. [D, §7]

**GRID-06.** Средние для графиков и исторического сравнения рассчитываются по явно заданной полной сетке, набору маршрутов и типам дней. Сводные средние из S относятся к присутствующим положительным строкам и не переносятся как средние по всем календарным часам. [S, §5–7; D, §6–7]

**GRID-07.** В потоке отсутствие события не означает завершённый нулевой час. Хранятся отдельно статус закрытия временного окна, доступная сумма и качество покрытия. Поздние события формируют новую версию наблюдений.

## 6. Хранилище и модель чтения

### Сущности и таблицы

- `DatasetManifest`: файлы, контрольные суммы, схема, политика времени, границы и отчёт проверок.
- `TargetRoute`: публичный номер, принадлежность конкурсному набору, поддержка истории.
- `RouteHourObservation`: ключ маршрута и часа, successful validations, происхождение, качество, версия данных.
- `NetworkSnapshot`: источник, дата актуальности, временная применимость, качество геометрии.
- `Stop`, `RoutePattern`, `StopOccurrence`, `ReferenceSegment`: справочные объекты сети.
- `ModelArtifact`: схема признаков, цель, горизонты, границы обучения, политика доступности, хеш модели.
- `ForecastRun`, `RouteHourForecast`: выпуск и неизменяемые значения прогнозов.
- `IngestionBatch`, `Job`, `StreamEvent`, `ExportArtifact`: служебные сущности.

**STORE-01.** Raw хранится отдельно от рабочих агрегатов. Parquet используется для истории и воспроизводимых выпусков; небольшая служебная БД — для заданий, манифестов и статусов.

**STORE-02.** Рабочая история может представляться плотным read-only NumPy-массивом `10 × 7296`. Один массив int64 занимает 583 680 байт; это не полный расход памяти приложения.

**STORE-03.** Для быстрых сумм допускаются накопительные суммы по часам и готовые суточные агрегаты. Маски качества и отсутствия данных хранятся отдельно, чтобы сумма не скрывала неполноту.

**STORE-04.** Новый снимок собирается и проверяется отдельно, после чего атомарно публикуется ссылка на его манифест. Одновременный запрос не читает наполовину изменённые массивы.

**STORE-05.** Кэш ограничен по памяти и количеству версий. Ключ включает snapshot, metric, routes, time, aggregation; географические ключи добавляются только для геометрических ответов.

## 7. Модельная часть и горизонты

**ML-01.** Сохраняется общий контракт прогнозного эксперта. Первая реализация — сезонный baseline и табличная модель; ансамбль добавляется при подтверждённом улучшении. GNN, реконструкция OD и поведенческая модель не являются обязательной зависимостью route-hour прогнозирования.

**ML-02.** В дополнение к дневному и месячному профилям вводится обязательный `competition_61d`: фиксированный 61-дневный прогноз без получения фактических будущих значений.

**ML-03.** Локальный контроль: более ранние временные отрезки для настройки, затем зафиксированный прогноз сентября–октября из состояния на конец августа. После выбора решения — переобучение на январе–октябре и прогноз ноября–декабря. [D, §2, §11]

**ML-04.** В будущем недоступны фактические лаги, число гаражных номеров, тарифные доли и отказы целевого часа. Используются признаки относительно момента выпуска, известный календарь или собственные промежуточные прогнозы.

**ML-05.** Внешняя погода: для следующего дня допустим реально доступный прогноз; для 61 дня нельзя подставлять фактическую погоду будущего периода. Все режимы фиксируются в манифесте эксперимента.

**ML-06.** Годовой выпуск — необязательная экспериментальная экстраполяция, если предусмотрен артефактом. По 10 месяцам одного года нельзя заявлять проверенную годовую сезонность. Это не возвращает в UI исключённый режим пользовательских сценариев. [D, §7, §10]

**ML-07.** Во внутреннем API прогнозы могут иметь дробные неотрицательные значения. Ограничение вместимости вагона к route-hour target не применяется. Точное требование к числовому формату конкурсного CSV подтверждается исходным README/платформой; округление не выполняется автоматически.

**ML-08.** Интервалы публикуются только при наличии соответствующей методики и проверки. Сумма отдельных P90 не выдаётся за P90 суммы.

## 8. Время доступности и аудит утечек

**TIME-01.** Различаются `event_time`, исходные `source_begin_time`/`source_input_time`, реальное `system_received_at`, модельные часы воспроизведения и момент выпуска прогноза.

**TIME-02.** Служебные даты содержат аномалии и большие задержки. `input_date_time` не является автоматически надёжным временем доступности признака. [D, §5]

**TIME-03.** Ретроспективная конкурсная проверка использует опубликованную историю по времени события и так обозначается. Она не доказывает, что весь этот набор уже поступил диспетчеру в соответствующий исторический момент.

**TIME-04.** Проверка реального потока использует зарегистрированное время поступления пакетов и явно объявленные предположения эмуляции. Отсутствующая история поступления не выдумывается.

**TIME-05.** Проверяется не только время признаков, но и границы обучения модели, преобразований, весов ансамбля и исторического среднего. Модель, обученная по октябрь, не применяется для честного теста выпуска на конец августа.

**TIME-06.** 523 сентябрьских успеха в train — особенность размещения данных; их правильное перемещение не является дополнительной меткой. 562 ноябрьских успеха исключаются из запуска с origin до ноября. Согласованность labels после объединения не подтверждает намеренную или случайную ошибку скрытого эталона. [D, §6]

**TIME-07.** `prediction` из sample submission — пример, не факт и не обучающий признак. [D, §6]

**TIME-08.** Справочные версии 2026 года и поздних месяцев 2025 года не распространяются назад для обучения и исторической реконструкции без подтверждения применимости.

## 9. Карта и справочники

**GEO-01.** Наличие прогноза и наличие геометрии хранятся независимо.

- Целевые маршруты с географией: `{1, 5, 7, 11, 12}`.
- Целевые без географии: `{17, 25, 26, 28, 50}`.
- Географические маршруты без конкурсного ряда: `{2, 3, 4, 6, 10}`. [D, §9]

**GEO-02.** Все 10 целевых маршрутов остаются в графиках, итогах и CSV. Отсутствие линии на карте не удаляет маршрут из числового результата.

**GEO-03.** Остановки соединяются по `stop_id`, не по названию. `trip_id` из данного справочника — шаблон, а не фактический рейс. [D, §8]

**GEO-04.** Для первых пяти листов справочника при чтении используется вторая строка заголовка, для `Порядок_с_координатами` — первая. Дополнительный лист является готовым представлением тех же связей и не увеличивает число остановочных посещений. [D, §8]

**GEO-05.** Координаты остановок доступны, точная траектория рельсов не предоставлена. Линия между остановками публикуется с `geometry_quality=schematic`, не как подтверждённая shape. [D, §9]

**GEO-06.** В обычном справочном режиме карта может показать имеющийся срез с датой и предупреждением. В строгом историческом режиме неподтверждённая для даты география не считается действующей.

**GEO-07.** Маршрутный прогноз разрешается визуализировать цветом вдоль маршрута, но он имеет `metric_scope=route`, `unit=validations/hour`. Легенда не называется процентом заполнения салона.

**GEO-08.** При выборе направления или участка `geometry_scope` меняется, а `metric_scope` остаётся route. В ответе явно указано `geometry_filter_affects_metric=false`; без согласованной подписи frontend не должен отображать это число как относящееся только к участку.

**GEO-09.** Запрос отдельного числового прогноза направления/остановки/перегона отклоняется как неподдержанный. Маршрутная сумма не дублируется в итогах по числу нарисованных линий.

**GEO-10.** `stop_mode`, числовое значение вместимости для категорий `БК`/`ОБК`, неизвестные единицы `shape_dist_traveled` не интерпретируются автоматически. Фрагменты наряда и расписания не связываются в фиктивное полное движение 2025 года. [D, §8]

## 10. API и изменения frontend-контракта

### Общий запрос

Числовые фильтры (`routes`, `metric`, `time_range`, `grain`, `aggregation`, `snapshot_id`) отделены от географического представления (`pattern_ids`, `section`, `bbox`, `reference_mode`). Неподдержанные числовые измерения не игнорируются молча.

### Общий ответ

Содержит `snapshot_id`, `metric`, `metric_scope`, единицу, интервал, правило агрегации, происхождение, флаги качества, поддержку истории и, для прогнозов, выпуск/модель. Географические ответы добавляют `network_snapshot_id`, временную применимость и список целевых маршрутов без географии.

### Возможности по умолчанию

- Успешные валидации по маршруту: доступны.
- Направление, остановка, перегон как отдельный числовой target: недоступны.
- Карта остановок: частично доступна, в справочном режиме.
- Присутствующие пассажиры и процент заполнения: недоступны.
- Дневной, месячный и 61-дневный прогноз: поддерживаются при наличии артефакта.
- Годовой: экспериментальный и отключаемый.
- Текущее положение вагонов: недоступно без нового источника.
- Дорожная обстановка: не включена в обязательную часть.

## 11. Экспорт и официальная оценка

**EXP-01.** Пользовательский экспорт фиксирует исходный snapshot и фильтры; данные соответствуют карте/графику по смыслу показателя, а не по количеству геометрических фрагментов.

**EXP-02.** Конкурсный экспорт отдельный: `route;date;hour;prediction`, 14 640 уникальных ключей, все 10 маршрутов, все часы 61 дня ноября–декабря. Порядок берётся из ключей шаблона; его колонка prediction игнорируется. [D, §2, §6]

**EXP-03.** Проверяются даты, часы 0–23, полный набор ключей, отсутствие повторов, пропусков, NaN/inf и отрицательных значений. Не добавляется индекс DataFrame. Файл формируется воспроизводимо из указанного выпуска и модели.

**EXP-04.** До любых фильтров frontend конкурсная сетка остаётся полной. Нельзя выгрузить для платформы только маршруты, видимые на карте.

**EXP-05.** Официальная метрика: `WAPE = sum(abs(y - pred)) / sum(y)`; `score = max(0, 1 - WAPE)`. Считается по полной заданной сетке, а не как среднее WAPE маршрутов. [D, §2]

**EXP-06.** При `sum(y)=0` WAPE подвыборки возвращается как неопределённый с отдельной суммой абсолютных ошибок. Для №5 нельзя автоматически публиковать идеальный процентный score.

## 12. Поток и воспроизведение

**LIVE-01.** Формат организаторского эмулятора пока не установлен отчётами. Входной адаптер выделяется отдельно; примеры Excel не объявляются спецификацией эмулятора.

**LIVE-02.** Собственный replay допустим как явно обозначенное воспроизведение истории. Сырые файлы не отсортированы по времени; их физический порядок не используется как хронология. Для масштабного replay заранее готовятся внешняя сортировка/разбиение и индекс времени. [D, §5]

**LIVE-03.** Обновляются маршрутные суммы и прогнозы. Из потока валидаций не генерируются координаты вагонов и реальные прибытия.

**LIVE-04.** Начальное состояние на момент replay содержит только ранее воспроизведённые события. Нельзя сначала загрузить полную историю как текущее состояние и затем добавить к ней те же события потоком.

**LIVE-05.** Версии наблюдений и прогнозов неизменяемы после публикации; исправления создают новые версии. Повтор подключения SSE не требует повторного учёта операций.

## 13. Архитектура Python и ООП

### Процессы

Один компактный API-процесс FastAPI/Uvicorn и ограниченный worker для подготовки/применения моделей, потока и экспорта. Полный raw-аудит — отдельная CLI-задача. В автономном профиле всё приложение запускается одним контейнером с подключённым томом; память и CPU считаются для всего контейнера.

### Основные классы

| Класс | Ответственность |
|---|---|
| `DatasetImporter` | Чтение labels/raw и происхождение записей |
| `RouteHourBuilder` | Официальный target и полная сетка |
| `LabelReconciler` | Ключи, суммы и границы |
| `TemporalPolicy` | Время события, cutoff и доступность |
| `FeatureBuilder` | Общие признаки обучения и применения |
| `ForecastEngine` | Артефакты, эксперты и горизонты |
| `RouteAnalyticsService` | Матрицы, срезы, суммы и исторические профили |
| `NetworkCatalogService` | Частичная и версионированная география |
| `CapabilityService` | Доступность с учётом данных и модели |
| `SnapshotStore` | Атомарная публикация и чтение версий |
| `ReplayService` | Контролируемое воспроизведение |
| `SubmissionService` | Полная конкурсная сетка и проверки |

Порты чтения, записи, моделей и источников описываются небольшими Protocol. Классы предметной области не зависят от HTTP и конкретного SQL. Используется композиция; глубокие универсальные иерархии не требуются.

Value objects допустимы для `TimeRange`, `RouteSection`, `MetricDefinition`, `ForecastOrigin`. Для 62 млн операций не создаются 62 млн объектов домена: чтение и вычисления пакетные.

Рекомендуемые каталоги: `api/`, `domain/`, `application/`, `pipelines/`, `infrastructure/`, `workers/`, `cli/`, `tests/`.

## 14. Производительность, ресурсы и надёжность

**PERF-01.** API не читает 10 ГБ raw, не обучает модель и не обращается к внешней погоде по обычному запросу карты.

**PERF-02.** Базовые ответы строятся из компактных индексов/массивов или подготовленных агрегатов. Геометрия передаётся отдельно от временных значений.

**PERF-03.** Ограничиваются модели в памяти, кэш, очередь заданий, SSE-буферы, количество одновременных вычислений, внутренние потоки числовых библиотек и размеры запросов/ответов.

**PERF-04.** CPU-bound задачи выполняются вне сетевого цикла. Async не рассматривается как замена пакетным вычислениям и контролю ресурсов.

**PERF-05.** Служебные операции подтверждаются после надёжного сохранения. При переполнении очереди возвращается контролируемая ошибка, а не растёт бесконечный буфер.

**PERF-06.** Цели из задания проверяются на одном контейнере с 2–4 vCPU и 2–4 ГБ RAM. Стартовый профиль нагрузки — 300 RPS и p95 ≤250 мс для объявленной смеси интерактивных запросов; это цель, не достигнутый результат.

**PERF-07.** Тесты выполняются с разными маршрутами/временем, отдельно с холодным и тёплым кэшем, совместно с приёмом событий и экспортом. Указывается реальный размер ответа. Быстрая постановка задания не считается быстрым завершением прогноза.

**PERF-08.** В README: ограничения контейнера, процессор, диск, версии, объём данных и моделей, RPS, p50/p95/p99, ошибки, CPU, память всего контейнера, состояние очередей, длительность, warm/cold режимы, команды воспроизведения.

**PERF-09.** Многорепличный профиль требует общего состояния заданий и согласованной обработки пакетов. Простое копирование контейнера с локальной SQLite не считается горизонтальным масштабированием.

## 15. Новые обязательные тесты

1. №5 не теряется при загрузке labels без положительных строк этого маршрута.
2. Восстанавливаются ровно 72 960 исторических ключей; отсутствующий будущий факт не становится нулём.
3. Успешная операция типа, отличного от 52, входит в target.
4. Повторяющиеся `tran_no` и `(device_no, tran_no)` не приводят к удалению разных исходных строк.
5. Повторный импорт того же файла и повторная доставка того же пакета не удваивают значения.
6. 523 сентябрьских успеха учитываются один раз; 562 ноябрьских не попадают в обучение до ноября.
7. Labels и raw-агрегаты совпадают по каждому историческому ключу и сумме.
8. `place_id` нельзя использовать для назначения остановки.
9. №50 21 сентября остаётся нулём официального target с флагом качества.
10. Все 10 маршрутов участвуют в экспорте, даже если на карте есть география только пяти.
11. Геометрический выбор участка не создаёт фиктивный пассажиропоток участка и не удваивает маршрутную сумму.
12. Запрос отдельного числового прогноза остановки возвращает явную причину недоступности.
13. Поздняя справочная топология не считается действующей в раннюю дату автоматически.
14. Изменение будущих данных не меняет выпущенный ранее прогноз; дополнительно проверяется cutoff обучения артефакта.
15. Фиксированный 61-дневный прогноз не получает реальные лаги из своего будущего периода.
16. Sample prediction не участвует в обучении и не подмешивается в результат.
17. Финальный CSV содержит ровно 14 640 ожидаемых ключей без индекса и недопустимых чисел.
18. Повторный запуск, падение worker и переподключение клиента не теряют подтверждённые данные.
19. Воспроизведение не добавляет операции к уже полностью загруженному факту второй раз.
20. Карта, графики и экспорт используют один snapshot и один смысл показателя.
