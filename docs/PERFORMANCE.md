# Производительность текущей поставки · 27.09.2026

Инженерная цель **300 RPS и p95 ≤250 мс** достигнута для проверенной смеси чтений готовых прогнозов с прогретым кэшем, в том числе во время обучения. Для 600 различных запросов истории после перезапуска API цель не достигнута. Замеры P0 сохранены в `archive/` и не относятся к этой версии.

## Среда и границы измерения

[Полная конфигурация и ID Docker image](performance-environment.json): AMD Ryzen 5 7500F, 6 физических ядер / 12 потоков, 33 203 101 696 байт RAM (30,92 ГиБ), Linux 7.0.12 CachyOS, Docker 29.5.2. Python 3.12, закреплённый `backend/uv.lock`; одна копия API, четыре HTTP worker-thread внутри одного процесса Uvicorn. Контейнеры: API **2 CPU / 2 ГиБ**, general worker **1 CPU / 2 ГиБ**, model worker **2 CPU / 6 ГиБ**. Ограничение ML-потоков — 2. Кэш числовых представлений — 64 записи / 64 МиБ; дополнительно ограниченные кэши матриц, метаданных, расписаний и пространственных профилей.

Генератор и сервис находятся на одном компьютере, связь — loopback `127.0.0.1:8083`. Хост не выделенный: уже существовавшие сторонние контейнеры оставлены работающими, отдельный `moscowt-verify` остановлен на время замеров. Внешняя сеть, браузерный рендеринг, TLS и балансировщик не измеряются. Это одиночные 30-секундные прогоны, не доказательство устойчивой производительности за сутки или на другом оборудовании.

## Обычные чтения

Open-loop генератор задаёт 300 запросов/с на 30 секунд, всего 9 000 запросов; максимум 96 активных клиентских корутин. Latency включает задержку генератора и ожидание в очереди, а не только время внутри сервера. После окончания подачи ожидается завершение всех запросов, поэтому достигнутый RPS в перегрузке ниже заданного.

Смесь `/api/v1`: по 20% `map-snapshot`, `timeseries`, `route-comparison`, `heatmap`; по 10% `capabilities`, `routes`. v1 использует канонические v2-данные и общий сервис числовых представлений. Дополнительно отправляется 6 фоновых CSV-экспортов на прогон; все завершились `ready`. Поле `checkedAfterSeconds` в JSON означает момент проверки статуса, а не фактическую длительность экспорта.

| Режим | Завершено | Фактический RPS | p50, мс | p95, мс | p99, мс | Ошибки |
|---|---:|---:|---:|---:|---:|---:|
| [Готовые прогнозы, тёплый кэш](performance-v2-warm.json) | 9 000 | 300,01 | 1,84 | **3,09** | 4,80 | 0 |
| [То же во время обучения](performance-v2-training.json) | 9 000 | 300,01 | 2,11 | **3,78** | 6,38 | 0 |
| [История, холодный кэш, много разных запросов](performance-v2-cold.json) | 9 000 | 263,05 | 2 153,27 | **4 119,70** | 4 353,30 | 0 |

Тёплый режим: 24 предварительно рассчитанных варианта, по 3 или 10 маршрутов, сутки/неделя ноября 2025; основной датасет содержит январь–октябрь, прогноз — ноябрь–декабрь. Холодный режим: API перезапущен, предварительного расчёта нет, 600 вариантов истории января–октября с дневными/полусуточными началами. Рабочий набор больше 64 записей кэша. Кэш файлов ОС не сбрасывался. Такой тест включает постоянные промахи, а не только первый запрос после старта; обработка заняла 34,21 с при 30 с подачи.

При параллельном обучении использован полный сервисный LGB/CB/RF с новым seed. Задание было `running` в начале и в конце нагрузки, опубликованный снимок не менялся; после измерения обучение отменено. Скорость самого обучения этим тестом не оценивается.

Выборочные `docker stats`: максимум памяти API 191,9 / 217,2 / 219,5 МиБ для тёплого / обучения / холодного режима; максимум CPU 54,40% / 64,17% / 112,19%. В Docker 100% соответствует одному логическому CPU; это выборочные пики, не непрерывный high-water mark. Размер ответов: до 133 683 байт, средний около 15 КБ. Подробные пробы ресурсов и серверные histogram — в JSON.

## Отдельные запросы v2

[Протокол и тела запросов](performance-v2-extra.json). По 20 последовательных обращений, concurrency=1; первый показан отдельно, p50/p95 вычислены по последующим 19. На столь малой выборке p95 повторов совпадает с максимальным значением повторов. Это измерение latency; RPS при параллельном выполнении таких запросов не заявляется.

| Запрос | Первый, мс | p50 повторов, мс | p95 повторов, мс | Ошибки |

| День, 10 маршрутов, почасовые строки и происхождение | 70,23 | 65,55 | 103,71 | 0 |
| День с коэффициентами и бюджетом вагоно-часов | 67,89 | 67,29 | 109,99 | 0 |
| Годовой сценарий, суммы по месяцам | 535,85 | 530,41 | 791,23 | 0 |
| Участки маршрутов за день | 49,84 | 22,45 | 23,65 | 0 |

V2-экспортное представление возвращает более подробные строки и рассчитывает агрегацию/знаменатель по запросу. Его последовательные показатели нельзя подменять RPS кэшированной карты. Для массового скачивания предназначены фоновые экспорты. Годовой результат остаётся невалидированным сценарием независимо от времени ответа.

## Воспроизведение

Нужен готовый demo-снимок в отдельном Compose project и Python dev-зависимости из `backend/uv.lock`. Выполняйте прогоны последовательно, без параллельных тестов/сборок:

```bash
MOSCOWT_PORT=8083 docker compose -p moscowt-release up -d --build --wait
backend/.venv/bin/python backend/scripts/load_test.py --url http://127.0.0.1:8083 --container moscowt-release-api-1 --mode warm --rps 300 --seconds 30 --exports --output docs/performance-v2-warm.json
backend/.venv/bin/python backend/scripts/benchmark_platform.py --url http://127.0.0.1:8083 --output docs/performance-v2-extra.json
backend/.venv/bin/python backend/scripts/benchmark_during_training.py --url http://127.0.0.1:8083 --container moscowt-release-api-1 --output docs/performance-v2-training.json
docker restart moscowt-release-api-1
# Дождитесь статуса healthy, затем выполните холодный прогон:
docker inspect --format '{{.State.Health.Status}}' moscowt-release-api-1
backend/.venv/bin/python backend/scripts/load_test.py --url http://127.0.0.1:8083 --container moscowt-release-api-1 --mode cold --rps 300 --seconds 30 --exports --output docs/performance-v2-cold.json
```

Во время проверки обнаружено и устранено полное копирование всех координат Москвы при каждом запросе метаданных. Теперь копируются изменяемые записи маршрутов/направлений; геометрия остаётся неизменяемой. Тесты проверяют независимость дат и исходной сети. Для большого числа уникальных интервалов ограничителем остаётся вычисление представлений; дальнейшее масштабирование требует отдельного профилирования этого режима, предварительной агрегации или другого распределения процессов. Увеличивать число HTTP-потоков без повторного замера не рекомендуется.
