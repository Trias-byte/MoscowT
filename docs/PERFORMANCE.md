# Производительность одного контейнера · 27.09.2026

API, general worker и model worker работают **в одном контейнере с общим лимитом 4 vCPU / 4 ГиБ**. `memswap_limit=mem_limit` запрещает swap. Готовая поставка запускается без обучения и внешних сайтов. Фактические замеры подтверждают сотни RPS с p95 ниже 200 мс **для описанной прогретой смеси готовых прогнозов**, в том числе при параллельной обработке входных данных.

## Среда и метод

AMD Ryzen 5 7500F (6 ядер / 12 потоков), 30,92 ГиБ RAM, Linux 7.0.12, Docker 29.5.2, Python 3.12. [Конфигурация контейнера, image ID и SHA-256 исходников](performance-single-environment.json). [Compose](../compose.single.yaml): один API, два worker, ML до двух потоков. Предыдущие контейнеры проекта остановлены; сборки и браузерные тесты во время замеров не запускались. Генератор работает на том же компьютере через loopback `127.0.0.1:8083`; обычные приложения пользователя остаются открытыми.

Open-loop, 96 клиентских обработчиков, 24 прогретых варианта периодов/маршрутов. Смесь: `/api/v1/map-snapshot`, `timeseries`, `route-comparison`, `heatmap` — по 20%; `capabilities`, `routes` — по 10%. Числовой кэш ограничен 64 записями / 64 МиБ; география и матрицы имеют отдельные ограниченные кэши. p95/p99 включают ожидание планировщика генератора; HTTP-ошибки и исключения учитываются. RPS в таблице относится к чтению; HTTP загрузки, задания и их опрос идут дополнительно.

При чтении с приёмом событий CPU ниже 60–80% выделенной квоты; запас сохранён. Опыты не определяют предельную точку насыщения сервиса.

**Swap — 0 байт во всех наблюдениях, OOM / OOM kill — 0.** Рабочая память после заполнения кэшей колеблется в указанных пределах. Полные значения `memory.current`, `memory.swap.current` и `memory.events` сохранены в JSON; `memory.current` включает файловый кэш и отличается от Docker working set. Многосуточный soak-test не проводился; отсутствие утечек на произвольной длительности не заявляется.

## Приём потоковых данных

Один последовательный producer отправляет по **10 000 синтетических сырых событий валидации** (350 070 байт CSV, HTTP chunked по 16 КиБ). Пакеты относятся к десяти тестовым маршрутам и непересекающимся часовым интервалам. Путь: `/api/v2/blobs` → очередь предварительной проверки → применение → нормализованный Parquet и новая неизменяемая редакция набора. Создаётся отдельный неопубликованный набор; реальные данные и модель не переключаются. Следующий пакет начинается после сохранения предыдущего.

| Чтение параллельно | Пакеты / исходные события | Обработано событий/с | p95 приёма файла, мс | p95 до сохранения редакции, с |
|---|---:|---:|---:|---:|
| 300 RPS | 27 / 270 000 | 4355 | 31.70 | 2.77 |
| 600 RPS | 26 / 260 000 | 4270 | 196.59 | 2.92 |

Производительность событий считается по полному времени обработки, включая последний пакет, завершившийся после окна нагрузки. Проверены отбор всех исходных записей, число нормализованных маршрутно-часовых строк, сумма успешных валидаций и неизменность рабочего выпуска/выбранного набора. Все пакеты сохранены без повторного зачёта. Это HTTP-пакеты, не заявленная поддержка Kafka/WebSocket и не online-learning. Время приёма файла отделено от времени до сохранения редакции: обработка пакета занимает секунды и не включается в обещание p95 готовых чтений.

Во время каждой минутной нагрузки создано 12 CSV-выгрузок; во время обучения — 6. Все завершились. General worker чередует задания v2 и совместимые экспорты v1, предотвращая голодание выгрузок при непрерывном импорте. Статусы на конце нагрузки и после дренирования очереди есть в протоколах.

При обучении использован LGB/CB/RF 1378/332/300 с новой seed, теми же историческими данными и погодными признаками. Задание было `running` до и после 30-секундного чтения; затем отменено, основной выпуск не изменился. Этот тест измеряет чтение во время обучения, а не полную длительность обучения.

Массовые выгрузки обрабатываются очередью.

## Воспроизведение

Запускать последовательно на изолированной поставке; нагрузка создаёт тестовые наборы и задания:

```bash
MOSCOWT_PORT=8083 docker compose -f compose.single.yaml -p potok-single-verify up -d --build --wait
backend/.venv/bin/python backend/scripts/load_test.py --url http://127.0.0.1:8083 --container potok-single-verify-service-1 --mode warm --rps 300 --seconds 60 --exports --ingestion --output docs/performance-single-300.json
backend/.venv/bin/python backend/scripts/load_test.py --url http://127.0.0.1:8083 --container potok-single-verify-service-1 --mode warm --rps 600 --seconds 60 --exports --ingestion --output docs/performance-single-600.json
backend/.venv/bin/python backend/scripts/benchmark_platform.py --url http://127.0.0.1:8083 --output docs/performance-single-extra.json
backend/.venv/bin/python backend/scripts/benchmark_during_training.py --url http://127.0.0.1:8083 --container potok-single-verify-service-1 --output docs/performance-single-training.json
```

Зависимости генератора: `cd backend && uv sync --frozen --extra models`. HTTP без TLS, браузерный рендеринг, внешняя сеть, множество одновременно уникальных запросов и горизонтальное масштабирование не измерены. SQLite и файловые блокировки рассчитаны на один хост и один worker каждого канала.

Прежние `performance-scenarios-*.json` измеряли API с отдельными worker-контейнерами. `performance-v2-*.json` и P0 относятся к ещё более ранним версиям. Их показатели не используются как результаты этой поставки.
