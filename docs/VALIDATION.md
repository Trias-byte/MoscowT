## Команды

Из корня репозитория:

```bash
cd backend
uv sync --frozen --extra models --python 3.12
uv run pytest -q
uv run ruff check src tests scripts
cd ../frontend
npm ci
npm test
npm run build
npx playwright install chromium
cd ..
MOSCOWT_PORT=8082 docker compose -p moscowt-verify up -d --build
PLAYWRIGHT_BASE_URL=http://127.0.0.1:8082 MOSCOWT_E2E_MUTATIONS=true npm --prefix frontend run test:e2e
backend/.venv/bin/python backend/scripts/verify_platform.py --url http://127.0.0.1:8082 --source-dir ../dataset
backend/.venv/bin/python backend/scripts/verify_recovery.py --url http://127.0.0.1:8082 --project moscowt-verify
backend/.venv/bin/python backend/scripts/verify_bundle.py --url http://127.0.0.1:8082
backend/.venv/bin/python backend/scripts/evaluate_sources.py
backend/.venv/bin/python backend/scripts/evaluate_models.py
backend/.venv/bin/python -m pytest -q analysis/dataset/test_same_direction_stops.py
```

HTTP/E2E/recovery запускаются на отдельном Compose project: они временно меняют публикацию, добавляют данные и завершают процесс worker. `verify_platform.py` восстанавливает исходный активный выпуск в `finally`. После проверки достаточно `docker compose -p moscowt-verify stop`; чужие контейнеры и тома не затрагиваются.

Для тестов истории рядом с репозиторием нужны исходные `../dataset/labels`, `test_submission.csv` и справочники; для HTTP-приёмки используется нормализованное расписание из demo-архива, созданное из предоставленного `moscow_tram_schedules.csv`. Для первого запуска готового приложения эти внешние файлы не нужны: данные и модели включены в demo-архив.

## Значимые инварианты

- `append/upsert/replace` имеют разные правила; повтор файла/спецификации не суммирует данные повторно. `complete=false` сохраняет пропуски.
- Модели получают историю до origin. Изменение будущих target и недоступных событий/погоды не меняет ранее выпущенный прогноз. Исторический event time не доказывает оперативную доступность исходной выгрузки: режим ретроспективы отмечен явно.
- RF при inference использует один поток, чтобы порядок суммирования деревьев не менял последние биты результата. После загрузки из Docker оба основных адаптера и годовой сценарий дали точно одинаковые массивы.
- Полные назначения объединяют интервалы одного физического вагона; ночные рейсы связываются со служебной датой. Неопределённое покрытие/конфликт не становится нулём или достоверным выпуском.
- Нейтральные множители сохраняют базу. Бюджет дополнительных часов определяется полным интервалом сценария и не меняется при запросе его подинтервала. Интенсивность считается отношением сумм.
- Остановочные доли сохраняют маршрутную сумму; участки описывают пересечения и неаддитивны. API карты и экспорт используют одну backend-методику.
- Выбор даты геометрии не изменяет immutable исходную сеть или ранее выбранную дату. В HTTP нет повторного копирования всех координат Москвы ради маршрутных метаданных.
- Полный архив фиксирует изменяемый указатель публикации до упаковки immutable зависимостей; одновременная новая публикация не повреждает manifest. Одновременное сохранение одинакового сценария возвращает один результат.
- Manifest модели публикуется после файла, активная карта не переключается при отмене/падении задания. Readiness проверяет наличие канонических разделов, модели и прогноза.

## Повторная проверка Docker-сборки после npm EIDLETIMEOUT

27.09.2026: установка 141 пакета с пустым BuildKit-кэшем завершилась за 4 с, TypeScript/Vite собраны. Повторная установка с тем же lockfile и сохранённым npm-кэшем при `--network=none` завершилась за 2 с; `npm ls --depth=0` успешен. Для повторного исполнения RUN использован изменяемый build argument в временном Dockerfile с теми же командами: `--no-cache-filter` в установленной версии BuildKit создавал новый пустой cache mount и не подходил для проверки тёплого кэша.

`docker compose build` завершился успешно. На пустых тестовых томах запущены API/general worker/model-worker, `/health/ready` вернул `ready`, frontend и четыре asset-файла — HTTP 200, каталог и прогноз доступны. Проверенный image: `sha256:406a4f0f23e3f6476947ce013ca604254738025bf90b53bd4bfa99ee6eee6382`; SHA-256 неизменённого `frontend/package-lock.json`: `b8b257e8bccd7d49402ccdaf9a64e53b0a4b9efd953f53219ffaf6fc0c29e3d1`.

Во время диагностики registry отвечал и на хосте, и в bridge-контейнере, поэтому постоянный сбой DNS не подтверждён. Кэш и повторные попытки помогают при временных сбоях, но первая загрузка отсутствующего пакета требует доступного registry. Инструкция для `MOSCOWT_BUILD_NETWORK=host` добавлена в README.

## Пределы доказательств

Ни один тест интерфейса не подтверждает фактическую остановочную точность, переполненность или качество годового прогноза. Периоды сентября/октября уже использовались при исследованиях и не являются независимым holdout. Уменьшенный ансамбль для source ablation и HTTP-приёмки отличается от полного сервисного рецепта; метрики опубликованы раздельно. Неподтверждённый трафик не подменяется искусственными числами.

В текущем закреплённом окружении pytest выдаёт предупреждения устаревания pandas/NumPy и Starlette/httpx; они не скрыты глобальным фильтром. Проверки проходят, но перед обновлением библиотек необходимо повторить тесты сериализации и прогнозов. Горизонтальное масштабирование и многосуточный endurance-тест не проводились.
