# Архитектура

Приложение состоит из React-интерфейса и Python API. Один Docker-образ содержит интерфейс, backend, зависимости, архив исходного состояния, нативные веса и пассажирский пакет. Запросы браузера идут на тот же адрес, с которого загружена страница.

## Процессы и состояние

`RuntimeBootstrap` восстанавливает исходное состояние в пустые тома и устанавливает включённые выпуски пассажирских данных и модели. Установка проверяет целостность и использует атомарные указатели. Повторный запуск сохраняет пользовательские публикации и ручной откат пассажирского пакета.

`ProcessSupervisor` запускает API, общий worker и worker моделей. Завершение любого дочернего процесса приводит к остановке группы. SIGTERM передаётся детям; после установленного срока оставшиеся процессы завершаются принудительно. Политика `restart: unless-stopped` управляет перезапуском контейнера.

В `STATE_DIR` находятся SQLite очередей, снимки, модели, результаты и экспорты. В `DATA_ROOT` — каталог редакций истории, разделы Parquet, погодные данные, расписания и пассажирские выпуски. Для них используются два именованных тома; исходники хоста контейнеру не монтируются.

## Запросы и задания

API v1 обслуживает карту, графики и совместимый экспорт. API v2 управляет данными, моделями, прогнозами и сценариями. Ответы строятся по идентификаторам неизменяемых версий. Кэш ограничен количеством записей и оценкой памяти.

Тяжёлые операции попадают в `WorkQueue`. Очередь хранит ключ идемпотентности, статус, владельца, срок аренды и контрольные точки. Worker забирает задания своего канала и запускает вычисление в отдельном процессе. `JobExecutor` связывает вид задания с доменным сервисом. Обновление модели может продолжиться по сохранённым контрольным точкам после прерывания.

На клиенте `ApiClient` выполняет запросы и проверяет JSON схемами Zod. TanStack Query управляет загрузкой и обновлением данных. React-компоненты остаются функциями; сервисы с зависимостями и состоянием реализованы классами. Чистые расчёты не требуют объектов с жизненным циклом.

## Данные и модели

`DatasetRepository` нормализует загрузку, показывает предварительный отчёт и сохраняет новую редакцию. Повторный импорт не удваивает значения. Изменение рабочего набора между предварительной проверкой и применением обнаруживается по версии.

`ModelService` работает через общий контракт адаптера. Доступны сезонный профиль, CatBoost/LightGBM/RandomForest, конкурсный CatBoost × 5 и годовой сценарий. Модель хранит редакцию истории, период, признаки, параметры и происхождение. `ModelPackageService` проверяет состав переносимого ZIP, хеши, форматы и совместимость истории.

`ScenarioForecastService` рассчитывает отдельный результат из выбранного прогноза и параметров сценария. Публикация меняет активный указатель только после завершения расчёта. Экспорт использует тот же сохранённый выпуск.

`PassengerRepository` читает компактные агрегаты. Индивидуальные идентификаторы карт в поставку приложения не входят. Сравнения категорий сверяются с основной историей; несовместимые редакции обозначаются в ответе.

## Автономность и ограничения

Frontend получает шрифты, справочную схему путей и Swagger UI из локальных статических файлов. Локальная карта показывает справочную схему трамвайных путей без уличной подложки; датированная геометрия трамвайных маршрутов приходит из API. Интернет нужен только для сборки программного окружения и явно запрошенного обновления внешних данных.

SQLite и файловые блокировки рассчитаны на процессы, работающие с общими локальными томами. Приложение не использует внешний PostgreSQL, Redis или облачное хранилище. Публичная многопользовательская эксплуатация потребует отдельного решения для авторизации; стандартный Compose публикует порт только на `127.0.0.1`.

Наблюдения — успешные валидации. Наполнение салона, направление конкретной поездки и посадка на конкретной остановке из этих данных не следуют. Годовой сценарий и поправки движения не являются доказанной причинной моделью.
