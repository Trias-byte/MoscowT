# Описание и анализ `dataset`

Дата анализа: 25 сентября 2026 года. Источник — локальные файлы папки `dataset` и описание задания. Исходные файлы не изменялись.

Отдельная проверка разделения train/test, доступности данных и лаговых признаков: [аудит временных утечек](TEMPORAL_SPLIT_AUDIT.md).

<!-- MEASURED_OVERVIEW -->
Проверены все восемь файлов, в том числе **62 443 497 строк сырых операций**. Основная разметка за январь–октябрь 2025 года содержит **59 667 191 успешных валидаций**. Число ненулевых почасовых значений — 57 551.

Наиболее существенные результаты:

1. Данных достаточно для маршрутного почасового прогноза и его агрегации по времени. Для фактической загрузки салона и остановочного пассажиропотока информации недостаточно.
2. В labels есть девять маршрутов. Для № 5 в сырых файлах найдена только одна неуспешная операция; полноценного обучающего ряда для него нет.
3. Готовая разметка точно воспроизводится после объединения исходных CSV и разбиения по времени события. В labels test уже включены 523 успешные операции начала сентября, физически лежащие в train.
4. Labels хранят только ненулевые часы. Для 10 маршрутов нужна полная сетка из 72 960 исторических часов.
5. Географический справочник покрывает пять из десяти целевых маршрутов. Расписание — только 15 остановок одного рейса, наряд — 15 строк за один день 2026 года.
6. Справочники отражают поздние версии маршрутов и остановок. Их нельзя автоматически считать исторически верными для всего обучающего периода.
7. Служебные даты и некоторые поля заполнены неоднородно; точные масштабы приведены ниже.

## 1. Что представляет собой набор данных

Основной массив — журнал операций валидаторов трамваев. Одна строка описывает попытку валидации: время, устройство, карту, результат, билетный продукт, маршрут и транспортное средство. Целевая величина организаторов — **число успешных валидаций**, условно называемое числом посадок:

```text
boardings(route, date, hour) = COUNT(*)
    WHERE validation_result = 1
    GROUP BY номер маршрута из ngpt_route,
             календарная дата tran_date_time,
             час tran_date_time
```

Это определение нужно отличать от нескольких других показателей:

| Показатель | Что можно установить |
|---|---|
| Успешные валидации за час на маршруте | Непосредственно посчитать из CSV; это конкурсный target |
| Уникальные карты | Посчитать по `crd_hashcode`; карта не гарантирует соответствие одному человеку |
| Все фактические посадки | Не наблюдаются полностью: нет сведений о пассажирах без зарегистрированной успешной валидации |
| Число пассажиров в салоне | Не восстанавливается напрямую: нет высадок и начальной загрузки |
| Посадки на конкретной остановке | Нельзя достоверно определить из основной таблицы: нет `stop_id` и координат события |
| Переполнение и необходимое число вагонов | Потребуются данные о загрузке по участкам, рейсах, интервалах и численной вместимости |

В папке есть готовые агрегаты и справочная топология части маршрутной сети. Полноценной истории GPS/ГЛОНАСС-телематики, фактического прохождения остановок, высадок и расписаний за январь–октябрь 2025 года нет.

## 2. Соотношение с заданием и конкурсной проверкой

В общем описании задания предусмотрены прогнозы на день, месяц и, опционально, год, а также остановочная детализация. Локальный `dataset/README.md` уточняет конкретный формат автоматической проверки: **почасовой прогноз для 10 маршрутов на 1 ноября — 31 декабря 2025 года**.

| Период по правилам | Файлы | Назначение |
|---|---|---|
| 01.01–31.08.2025, 243 дня | `train.csv`, `labels_day_train.csv` | Обучающая история |
| 01.09–31.10.2025, 61 день | `test.csv`, `labels_day_test.csv` | Доступная история для локальной проверки и подбора модели |
| 01.11–31.12.2025, 61 день | `test_submission.csv` содержит только пример прогнозов | Финальная конкурсная оценка по скрытому эталону |

Таким образом, `test.csv` здесь содержит известные результаты валидаций. После локальной проверки разрешено использовать историю train + test для финального прогноза. Скрытый тест — ноябрь–декабрь, а не файл с названием `test.csv`. Небольшие записи за границами заявленных периодов отдельно разобраны ниже; они не составляют полноценной истории будущих месяцев.

Метрика из README:

```text
WAPE = sum(abs(actual - prediction)) / sum(actual)
WAPE-score = max(0, 1 - WAPE)
```

Для неё имеют значение суммарные абсолютные ошибки, поэтому крупные маршруты оказывают существенное влияние на итоговую оценку. Индивидуальные нулевые часы не вызывают деления на ноль; для полностью нулевой отдельной выборки знаменатель WAPE равен нулю и требует специальной обработки. Заявленная оценка примера около 0,48 взята из README: проверить её без скрытого эталона невозможно.

## 4. Схема основных CSV

Оба файла имеют одинаковые 14 колонок, разделитель `;`, заголовок и кодировку UTF-8. Временные значения записаны строками `YYYY-MM-DD HH:MM:SS` без явного часового пояса. Для московской задачи логично трактовать их как локальное время Москвы, но сам формат этого не удостоверяет; интерпретацию нужно закрепить в контракте загрузки, не сдвигая часы автоматически как UTC.

| Поле | Смысл и рекомендуемый тип | Как использовать и чего избегать |
|---|---|---|
| `tran_no` | Номер транзакции, идентификатор | Не считать глобальным первичным ключом: номера повторяются |
| `device_no` | Идентификатор валидатора, строка/целое | Анализ источников и покрытия; число устройств не равно числу вагонов |
| `tran_date_time` | Время валидации, timestamp | Основной источник даты и часа target |
| `begin_date_time` | Служебное время начала поездки, nullable timestamp | Смысл задаёт README; расхождения с временем события и пропуски ограничивают применение |
| `input_date_time` | Время загрузки записи, nullable timestamp | Содержит аномальные даты; не использовать как время посадки |
| `crd_hashcode` | Обезличенный строковый идентификатор карты | Подсчёт разных карт и повторных валидаций; сохранять строкой без преобразования в число |
| `validation_result` | Код результата, целое | Только значение `1` входит в target; остальные коды не добавляют посадку |
| `tran_type_id` | Код типа транзакции, целое | Не ограничивать target только типом `52`: определение организаторов задаёт фильтр по результату |
| `place_id` | Код площадки/депо, идентификатор | **Не код остановки**; прямой связи со `stop_id` нет |
| `good_type` | Категория билета/тарифа, строка | Состав спроса, доли продуктов и исторические признаки |
| `pass_route` | Сырая цепочка пересадок, nullable string | Зашумлённое поле; не извлекать из него номер текущего маршрута или точную траекторию |
| `ngpt_route` | Название вида `25 трамвай`, строка | Извлечь число и получить аналитический ключ `route` |
| `bus_exit_no` | Номер выхода/графика, идентификатор | Потенциальное соответствие `grafic`, только вместе с маршрутом, датой и актуальным расписанием |
| `garage_number` | Гаражный/бортовой номер вагона, идентификатор | Потенциальное соответствие `depot_number`; не путать с `vehicle_id` или номером устройства |

Идентификаторы не являются непрерывными количественными признаками: среднее значение `device_no` или `garage_number` не имеет содержательного смысла. Для исходного слоя удобно сохранять такие поля строками, а для аналитического слоя назначать типы после проверки.

Пустое значение здесь — пустая строка CSV. `—` означает, что число разных временных значений отдельно не вычислялось; `*` — подсчёт по отпечаткам, см. методику.

Внешние пробелы у `good_type` встречаются в 3 280 672 строках (5,25 %). Перед группировкой категорий нужен `strip()`, сохраняя исходный текст для контроля. Пример: `30дн ММ+МГТ СКС ` с завершающим пробелом. Во всех строках `crd_hashcode` — 32 шестнадцатеричных символа; это не подтверждает, что каждый идентификатор соответствует отдельному человеку.

В объединении файлов 3 080 устройств и 490 непустых гаражных номеров. В test встречается 13 устройств, которых нет в train. Эти количества описывают всё окно наблюдений, а не одновременно работающий парк.

### Время события и служебные даты

| Поле | train: минимум → максимум | test: минимум → максимум |
|---|---|---|
| `tran_date_time` | 2025-01-01 04:29:40 → 2025-09-01 01:55:45 | 2025-09-01 04:20:19 → 2025-11-01 01:37:43 |

| Проверка | train | test |

| Начало поездки позже события | 11 776 878 | 3 314 417 |

Проверки пересекаются: строки «больше суток» и «больше 30 суток» нельзя складывать. Отсутствующие даты начала поездки в сравнения не входят.

Для `begin_date_time` встречаются годы от 1991 до 2126. Для `input_date_time` встречаются годы от 2025 до 2026. Большие задержки загрузки сами по себе не доказывают ошибку каждого события, однако они и крайние значения делают служебные даты непригодной заменой `tran_date_time`. Небольшое положительное смещение начала поездки также может отражать округление времени; причины в файлах не описаны.

Форматы всех непустых временных значений разбираются стандартным парсером. Значит, основная проблема служебного времени здесь — смысл и достоверность значений, а не синтаксис. Поздняя загрузка также означает, что доступная сейчас история не подтверждает полноту сведений, которыми диспетчер располагал в момент события. Для оценки работы в реальном времени нужен отдельный контроль задержек источника.

## 6. Готовая разметка и сетка прогнозирования

Несмотря на `day` в названии, `labels_day_train.csv` и `labels_day_test.csv` содержат **почасовые**, а не суточные агрегаты. Схема:

| Поле | Тип | Значение |
|---|---|---|
| `route` | int | Номер маршрута |
| `date` | date | Календарная дата |
| `hour` | int, 0–23 | Час начала интервала |
| `boardings` | int ≥ 0 | Число успешных валидаций в интервале |

Ключ — `(route, date, hour)`. В обоих файлах нет пустых полей, повторов этого ключа, отрицательных и явно записанных нулевых значений. Присутствуют только положительные агрегаты.

Полная историческая сетка для 10 маршрутов содержит `10 × 304 × 24 = 72 960` комбинаций. В labels записано 57 551: **15 409 комбинаций, или 21,12 %, отсутствуют**. Из них 7 296 приходится на маршрут № 5. Для модели нужны явные календарные часы, иначе лаг «предыдущие 24 строки» не будет означать предыдущие сутки.

После сверки с сырыми данными отсутствие успешных событий в выгрузке можно представить нулём целевой величины. При этом такой ноль означает отсутствие зарегистрированных успешных валидаций, а не доказанное отсутствие пассажиров или гарантированную полноту источника. Полезно отдельно хранить признак наличия исходных событий и флаг подозрительных провалов.

### Файл `test_submission.csv`

Содержит 14 640 уникальных ключей: `10 маршрутов × 61 день × 24 часа`. Поля — `route;date;hour;prediction`. Пропусков в сетке и отрицательных прогнозов нет. Числа в столбце `prediction` — пример модели, не наблюдаемые посадки.

Пример очень грубый: у каждого из девяти активных маршрутов всего три значения прогноза; у маршрута № 5 все 1 464 значения равны нулю. Например, для № 1 во все даты значения одинаковы внутри блоков 00–07, 08–15 и 16–23 часов: 349, 1 142 и 772. Такой шаблон подходит для проверки формата, но не отражает фактическую недельную и почасовую структуру спроса.

## 9. Как связаны источники и что доступно для карты

| Соединение | Ключ | Условия и ограничения |
|---|---|---|
| Сырые события → почасовой target | Номер из `ngpt_route`, дата и час `tran_date_time` | Фильтр `validation_result = 1`, явные временные границы |
| Номер маршрута → справочник маршрутов | `route` ↔ `route_short_name` | Привести типы, учесть версию маршрута |
| Маршруты → шаблоны | `route_id` | Соединение один-ко-многим |
| Шаблоны → остановки | `stop_id` | 622 позиции используют 489 уникальных остановочных пунктов |
| Расписание → шаблон | `trip_id`, `stop_sequence`, `stop_id` | В примере связь проверена; полного расписания нет |
| Валидации → график | `bus_exit_no` ↔ `grafic` | Возможное семантическое соответствие; необходимы маршрут, рабочая дата, версия и подтверждение источника |
| Валидации → транспортное средство | `garage_number` ↔ `depot_number` | Нужен исторический наряд на соответствующую дату; имеющийся пример относится к 2026 году |
| Площадка → остановка | Нет | `place_id` нельзя использовать как `stop_id` |

Целевые маршруты: `{1, 5, 7, 11, 12, 17, 25, 26, 28, 50}`. Справочник: `{1, 2, 3, 4, 5, 6, 7, 10, 11, 12}`. Пересечение — **`{1, 5, 7, 11, 12}`**. Не хватает географии для `{17, 25, 26, 28, 50}`; для `{2, 3, 4, 6, 10}` есть география, но нет целевого временного ряда.

Маршруты с доступной географией дают 50,11 % посадок по labels. То есть география отсутствует примерно для половины наблюдаемого объёма, включая самый крупный маршрут № 17.

На карте можно показать остановки и порядок их следования. Соединение соседних остановок прямыми линиями будет схемой маршрута: точная траектория рельсов, например отдельная таблица `shapes`, не предоставлена. Нельзя выдавать раскладку маршрутного прогноза по остановкам по произвольным весам за прогноз, обученный на реальных остановочных наблюдениях.

| Карта остановок | Частично есть | Доступны справочные остановки только пяти целевых маршрутов и поздние версии топологии |
| Прогноз на остановке или участке | Нет наблюдаемого target на этой детализации | Нужна дополнительная геопривязка событий и проверяемая остановочная история |
| Определение переполнения салона | Нет высадок, фактических рейсов и численной вместимости | Почасовой поток по маршруту не равен загрузке конкретного вагона |
| Нормализация исторических валидаций | Есть основные поля | Можно построить надёжный слой маршрутных агрегатов |
| Геопривязка по расписанию | Имеются только небольшие примеры | Нужны исторические расписания, календарь обслуживания, наряды и желательно фактическая телематика |

## 11. Требования к подготовке данных, следующие из анализа

1. **Сохранить исходную семантику.** Хранить слой событий с именем файла и номером строки. Чётко отличать время события, служебное время и время загрузки.
2. **Назначить схему и контролировать разбор.** CSV читать с `sep=';'`; идентификаторы сохранять без потери строкового представления; результаты разбора дат и маршрутов проверять отдельно от пустых полей.
3. **Зафиксировать временные окна.** Сначала объединить источники, затем разделить агрегаты по дате события: часть сентябрьских событий находится в train.csv и уже учтена в labels test. Не определять период только по имени файла и не включать неполный хвост ноября в обучающую историю перед конкурсным прогнозом.
4. **Считать target по результату валидации.** Не исключать успешные операции другого `tran_type_id` и не считать отказы посадками. Не дедуплицировать журнал по одному `tran_no` или только по карте и минуте.
5. **Построить календарную сетку.** Добавить отсутствующие ключи 10 маршрутов × сутки × 24 часа; отдельно сохранять покрытие источника и спорные провалы. Для № 5 явно отметить отсутствие положительного обучающего ряда.
6. **Сверять агрегаты.** Контролировать суммы и ключи против labels, границы train/test и результаты загрузки по маршрутам и датам. Аномальные периоды не удалять молча.
7. **Считать признаки только из доступного прошлого.** Лаги и скользящие статистики должны иметь временной сдвиг. Число вагонов, карточные доли и другие характеристики прогнозируемого часа нельзя брать из факта этого часа.
8. **Разделять два режима прогноза.** Для следующего дня можно опираться на свежую историю. Для 61 дня вперёд фактические лаги внутри будущего периода недоступны: способ их формирования и локальная проверка должны соответствовать этому условию.
9. **Проверять качество последовательно по времени.** Файл test использовать как отложенный сентябрь–октябрь; для подбора — более ранние временные срезы. Не перемешивать часы случайным train/test split. После выбора подхода можно переобучиться на январе–октябре.
10. **Версионировать справочники.** Не распространять срез 2026 года на всю историю 2025 года без оговорки. Отдельно хранить отсутствие географии, неизвестную связь и подтверждённое соединение.

Для практической работы с основным прогнозом необязательно каждый раз перечитывать около 10 ГиБ событий: проверенные почасовые labels содержат менее 58 тысяч строк. Большой журнал нужен для контроля качества и дополнительных исторических признаков. Обрабатывать его целиком как таблицу строк в оперативной памяти не требуется; при текущем анализе применено чтение порциями.

## 13. Методика и воспроизводимость

Основные CSV прочитаны полностью порциями по 250 000 строк, без пропуска ошибочных строк. Проверены схема, пустые поля, строковые категории, форматы времени, временные границы, порядок событий и агрегация успешных валидаций. Все строки labels, submission и всех Excel-листов прочитаны целиком. Проверены уникальность ключей, полнота сетки и связи справочников.

Для больших множеств карт, составных ключей и полных строк применены 64-битные отпечатки `pandas.util.hash_pandas_object`. Это практическая проверка повторов и количества разных значений, а не доказательство отсутствия хеш-коллизий. Категориальные счётчики, количества строк, суммы, почасовые сверки и проверки малых таблиц посчитаны непосредственно по значениям. Внешняя проверка движения маршрутов и правильности координат не выполнялась; причины обнаруженных изменений спроса из файлов не установлены.

Результаты расчётов лежат рядом с описанием:

- `raw_profile.json` — профиль CSV и сверка с labels;
- `small_files.json` — профиль разметки и шаблона ответа;
- `summary.json` — временные профили и проверки справочников;
- `workbooks.json` — размеры, поля, заполненность и число разных значений в Excel;
- `reconciliation.json` — итоговая сверка объединённой истории с labels;
- `route_summary.csv`, `monthly_summary.csv`, `monthly_by_route.csv`, `monthly_daily_average_by_route.csv`, `hourly_profile.csv`, `daily_by_route.csv` — сводные показатели;
- `train_hourly_from_raw.csv`, `test_hourly_from_raw.csv` — контрольные агрегаты сырых событий;
- `train_label_mismatches.csv`, `test_label_mismatches.csv` — все отличающиеся ключи, включая записи за границами заявленного периода;
- `profile_dataset.py`, `summarize_dataset.py`, `finish_report.py` — полный профиль, сводные расчёты и обновление измеренных разделов отчёта соответственно. Выполняются в этом порядке; нужны Python, pandas, NumPy и openpyxl. Для анализа использован pandas 2.2.3.

Исходное описание правил: `dataset/README.md`. Статистические показатели отчёта рассчитаны по локальным файлам, а не взяты из заявленных организаторами объёмов.
