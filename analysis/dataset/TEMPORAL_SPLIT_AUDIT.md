# Проверка временного разделения и утечек

Проверка разделения **train/test** от 25 сентября 2026 года. Проверены данные, правила конкурса и существующий код проекта. Исходные файлы не изменены; модель не обучалась.

**Вывод: готовые labels разделены по времени корректно. Использование сырых CSV целиком создаёт утечки через границы прогнозируемых периодов.** Дополнительно обнаружены риски доступности данных, поздних справочников и построения лагов. Ошибки в конкретной модели пока проверить невозможно: её обучающего пайплайна в проекте нет.

## 1. Критерии проверки

Утечка — использование сведений, недоступных в момент выпуска прогноза. Поэтому проверяется не только время события, но и время появления информации. Нормализация, заполнение средним, отбор признаков и другие обучаемые преобразования должны обучаться только на train соответствующего среза. [Определение и правила scikit-learn](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage).

Проверка должна воспроизводить горизонт и правила обновления прогноза. Прогноз следующего часа с обновлением после каждого факта и прогноз сразу на 61 день — разные эксперименты. Для оценки используют последовательные моменты выпуска с обучением только на доступном прошлом. [Hyndman и Athanasopoulos: Time series cross-validation](https://otexts.com/fpp3/tscv.html).

Контракт для момента выпуска `O`:

```text
Конец каждого обучающего целевого интервала <= O.
Исторические наблюдения для признаков доступны к O.
Целевые интервалы проверки начинаются в O или позже.
Будущие календарные и плановые признаки допустимы,
если именно эта их версия была известна к O.
```

При обновляемом прогнозе собственный `O` назначается каждому выпуску.

### 2.1. Утечка из raw train в сентябрьский test

Момент выпуска двухмесячного проверочного прогноза — 1 сентября в 00:00. Но `train.csv` содержит события 1 сентября до **01:55:45**. Они лежат после момента выпуска и уже учтены в `labels_day_test.csv`.

Например, маршрут № 11 в 00:00–00:59 1 сентября имеет target **122 посадки**. Все 122 находятся в raw train. У маршрута № 17 в этот час target **131**, также полностью присутствующий в raw train. Все 15 таких ключей сохранены в `test_labels_exposed_in_raw_train.csv`.

**Обучение или расчёт исторических признаков по всему raw train нарушает границу прогноза.** Обучение только по labels train не содержит этой утечки. Проверка `max(time_raw_train) < min(time_raw_test)` здесь проходит, но не защищает оценку по labels: её целевой период начинается раньше начала физического raw test.

523 посадки — **0,0041 %** объёма labels test. Это размер обнаруженного пересечения, а не измеренный эффект на качество модели. Влияние на метрику без эксперимента не установлено.

### 2.2. Утечка из raw test в ноябрьский прогноз

Для финального выпуска 1 ноября в 00:00 история должна заканчиваться октябрём. Однако raw test продолжается до **1 ноября 01:37:43**. Обучение на всём объединении train + test включит 562 реальные посадки из будущего конкурсного периода.

Опубликованные labels заканчиваются 31 октября и этого хвоста не содержат. При подготовке конкурсной истории нужно исключить `tran_date_time >= 2025-11-01 00:00:00`. Более поздний оперативный прогноз может использовать уже поступившие ноябрьские факты, но это другой момент выпуска и другой эксперимент.

### 2.3. Правильная реконструкция split

Сентябрьский хвост train нужно перенести в проверочную историю, а не потерять. Детерминированно объединяем события, агрегируем успешные валидации по `tran_date_time`, затем разделяем по календарным границам:

```text
train:          2025-01-01 00:00 <= t < 2025-09-01 00:00
test/holdout:   2025-09-01 00:00 <= t < 2025-11-01 00:00
финальный test: 2025-11-01 00:00 <= t < 2026-01-01 00:00
```

После этого вся опубликованная разметка совпадает по каждому ключу. Проверяемые суммы:

```text
train labels = 46 913 233 - 523 = 46 912 710
test labels  = 12 754 520 - 562 + 523 = 12 754 481
```

Объединение для подсчёта и распределения по датам допустимо. Обучение статистических преобразований на всей объединённой истории перед локальной проверкой — отдельная операция, которая создаст утечку.

## 3. Доступность данных на момент выпуска

Повторный проход по всем сырым CSV проверил условие: событие произошло **до** момента выпуска, но его `input_date_time` указан **в этот момент или позже**.

| Момент выпуска | История событий | Всего таких операций | Из них успешных |
|---|---|---:|---:|
| 01.09.2025 00:00 | Январь–август | **563 966** | **551 958** |
| 01.11.2025 00:00 | Январь–октябрь | **223 850** | **218 924** |

Для второй строки учтены оба файла: 71 336 операций из raw train и 152 514 из raw test. Ноябрьские события сюда не входят: это именно старые события с поздней датой загрузки. Форматы обоих временных полей разобраны во всех 62 443 497 строках.

Отдельно проверено точное совпадение с границей: 1 сентября таких загрузок нет, 1 ноября их две, обе успешные. При условии, что поступление ровно в момент выпуска уже доступно модели, число загрузок **строго позже** 1 ноября составляет 223 848 операций, в том числе 218 922 успешные валидации.

Это **риск использования ещё не поступивших сведений**, если `input_date_time` действительно означает время доступности. Но поле содержит аномалии, выявленные в предыдущем анализе. Поэтому оно не позволяет надёжно восстановить состояние системы на момент прогноза. Поздняя дата загрузки не доказывает, что факт впервые стал известен именно тогда; ранняя дата также не гарантирует своевременную доступность модели.

Для конкурса ретроспективная история считается доступной в рамках условий организаторов. Для проверки диспетчерского сервиса нужны надёжный `available_at`, журнал поступления или сохранённые снимки признаков. Исторические обучающие target должны быть доступны к моменту выпуска; окончательные факты test могут использоваться позже для оценки.

## 4. Лаги: положительного сдвига недостаточно

Для прогноза всего сентября–октября из 1 сентября нельзя подставлять фактические сентябрьские значения в лаги. Например:

```text
target: 15 сентября 08:00
lag_24h: фактические посадки 14 сентября 08:00
```

В момент выпуска 1 сентября 14 сентября ещё не наступило. Допустимы рекурсивно предсказанный лаг, признаки из истории до момента выпуска или модель с явным горизонтом прогноза.

Проверка на полной сетке test — **14 640 маршрутно-часовых ключей**:

| Фактический лаг | Недоступен для единого прогноза на 61 день | Доля |
|---|---:|---:|
| 1 час | 14 630 ключей | **99,93 %** |
| 24 часа | 14 400 | **98,36 %** |
| 168 часов | 12 960 | **88,52 %** |
| 720 часов | 7 440 | **50,82 %** |
| 1 464 часа | 0 | 0 % |

Это математическая проверка доступности источников признаков, а не найденный дефект существующей модели. Предполагается идеальная нулевая задержка: факт становится известен сразу после завершения часа. Рекурсивно предсказанный лаг не считается фактическим наблюдением и под эту проверку не подпадает.

При суточном выпуске в полночь `lag_24h` проходит временную границу для всех 24 часов. `lag_1h` недоступен для **23 из 24 часов**. При ежечасном выпуске `lag_1h` может быть допустим для следующего часа, если завершившийся час уже получен и обработан.

Скользящее среднее, включающее текущий target, и центрированное окно с будущими значениями создают прямую утечку. Для следующего часа нужен сдвиг перед окном; официальный пример использует `shift(1).rolling_mean(...)`. Для длинного горизонта дополнительно ограничивается момент выпуска. [Лаговые признаки в scikit-learn](https://scikit-learn.org/stable/auto_examples/applications/plot_time_series_lagged_features.html).

## 5. Разреженные часы и порядок строк

В исходных labels пропущены нулевые часы. На объединённых labels выполнен эксперимент: внутри маршрута сдвинуть timestamp на заданное число строк и измерить фактическую разность времени.

| Сдвиг строк | Сравнимых строк | Разность не равна ожидаемому числу часов | Медианная разность | Диапазон |
|---|---:|---:|---:|---|
| `shift(1)` | 57 542 | 2 721 — **4,73 %** | 1 час | 1–30 часов |
| `shift(24)` | 57 335 | 57 010 — **99,43 %** | **27 часов** | 24–62 часа |
| `shift(168)` | 56 039 | 56 039 — **100 %** | **187 часов** | 179–250 часов |

Это нарушение временного смысла лага; оно не обязательно использует будущее. Исправление: полная календарная сетка, явные правила нуля и флаги качества, затем сдвиги внутри маршрута.

Сортировка по `(route, timestamp)` подходит для этих сдвигов, но не делает всю таблицу глобально хронологической. `train_test_split(shuffle=False)` или `TimeSeriesSplit` поверх текущего порядка могут обучаться на августе одного маршрута и проверяться на январе другого.

Для общей модели нужно делить **уникальные временные метки**, затем включать в интервал все маршруты. Один целевой час не разделяется между train и test. Здесь 61 день — **1 464 временные метки** или **14 640 строк полной панели**.

`TimeSeriesSplit` использует порядок строк; временную равномерность обеспечивает пользователь. Параметр `gap` задаёт число исключаемых наблюдений, а `groups` не выполняет панельное разделение. [Документация TimeSeriesSplit](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html).

## 6. Нужен ли gap

**Обязательного зазора в 24, 48 или 168 часов только из-за автокорреляции нет.** Для непересекающихся почасовых target, прошлых признаков и своевременных данных соседние окна могут быть корректны с нулевым gap.

Зазор или исключение обучающих примеров определяются реальным механизмом:

- Если target — сумма за следующие 24 часа, нужно исключить обучающие примеры, чей целевой интервал пересекает test. Проверяется конец target, а не только timestamp строки признаков.
- Если признаки используют будущие точки окна, нужно исправить само окно.
- Если факты приходят с задержкой, нужно воспроизвести доступность информации к моменту выпуска.

Gap сам по себе не делает фактические сентябрьские лаги допустимыми для прогноза, выпущенного 1 сентября. Это вывод из условия доступности информации, а не перенос значения зазора из учебного примера.

## 7. Справочники и повторяющиеся сущности

У справочников проверено поле `actual_date`:

| Лист | Всего записей | Дата актуальности ≥ 01.09.2025 | Дата актуальности ≥ 01.11.2025 |
|---|---:|---:|---:|
| Маршруты | 10 | **10** | **9** |
| Остановки | 489 | **147** | **67** |
| Порядок остановок | 622 | **622** | **594** |
| Наряд | 15 | **15** | **15** |

Лист порядка с координатами повторяет те же 622 позиции. Даты актуальности доходят до февраля 2026 года.

Если из поздних срезов строить признаки для исторического прогноза, возникает риск использования изменений, ещё неизвестных на момент выпуска. Поздняя дата обновления сама по себе не доказывает, что каждое поле ранее было неизвестно. Нужны версии справочников или подтверждение исторической доступности конкретных сведений. Отображение среза на демонстрационной карте само по себе не является утечкой в модель.

Между raw train/test есть около **1 229 081 общего хеша карты**, а также общие устройства и вагоны. Для будущего спроса на существующей сети это ожидаемо и не означает утечку. Разделение по картам проверяло бы другую задачу — перенос на ранее не наблюдавшихся пассажиров.

У `(device_no, tran_no)` **282 292** общих значения между файлами при отсутствии совпадений полных строк. Эта пара не является надёжным глобальным ключом события, а её пересечение не доказывает дублирование фактических операций.

`test_submission.csv` содержит прогнозные числа на будущие даты. Это не доказательство утечки: таблица является примером ответа, а не фактическим target. Происхождение baseline по одним его значениям установить нельзя.

## 8. Предлагаемый протокол оценки

Для конкурса — прогноз на **61 день из фиксированного момента**, без чтения новых фактических target внутри окна. Пример срезов; все даты — 2025 год, обучение начинается 1 января, правые границы не включаются:

| Назначение | Момент выпуска / конец train | Начало проверки | Конец проверки | Ключей прогноза |
|---|---|---|---|---:|
| Разработка | 01.05 00:00 | 01.05 00:00 | 01.07 00:00 | 14 640 |
| Разработка | 01.06 00:00 | 01.06 00:00 | 01.08 00:00 | 14 640 |
| Разработка | 01.07 00:00 | 01.07 00:00 | 31.08 00:00 | 14 640 |
| Заключительная локальная проверка | 01.09 00:00 | 01.09 00:00 | 01.11 00:00 | 14 640 |

Окна разработки частично перекрываются; их оценки зависимы и не являются независимыми повторениями эксперимента. Июльский срез заканчивается 30 августа включительно, чтобы сохранить ровно 61 день.

Если по сентябрю–октябрю многократно выбирать модель, окно становится validation, а не независимым test. Скрытый ноябрь–декабрь остаётся окончательной внешней проверкой. После фиксации подхода можно переобучиться на всей разрешённой истории января–октября.

Для сервиса отдельно нужны выпуски на следующие 24 часа и на месяц. Качество ежечасного обновления нельзя выдавать за качество неизменяемого прогноза на сутки или два месяца.

WAPE следует считать по полной сетке, включая нули, и дополнительно показывать ошибки по маршрутам и горизонту. Исключение нулевых часов скрывает ошибки ложного положительного прогноза. Для № 5 с нулевой суммой target маршрутный WAPE не определён; абсолютную ошибку показать можно.

## 9. Контроли для будущего пайплайна

| Контроль | Условие |
|---|---|
| Target train | Конец каждого целевого интервала ≤ момент выпуска |
| Исторические признаки | Источник и конкретная версия доступны к моменту выпуска |
| Лаги | Сдвиг равен указанному числу часов, не переходит на другой маршрут |
| Длинный горизонт | Реальные target внутри будущего окна не читаются при прогнозировании |
| Преобразования | `fit` только на обучающей истории текущего среза |
| Панель маршрутов | Все маршруты одного часа входят в один временной срез |
| Сетка | Полный набор ключей, уникальность, явные нули и качество |
| Исходные файлы | Split задаётся временем, а не именем файла |
| Справочники | Используется версия, доступная на момент выпуска |
| Подбор модели | Окна разработки отделены от окончательной оценки |

## 10. Объём проверки и ограничения

Повторно прочитаны **все 62 443 497 операций** по четырём полям: время события, время загрузки, результат и маршрут. Заново рассчитанные часовые агрегаты совпали с предыдущим полным профилем. На малых таблицах выполнены точные проверки пересечений, доступности target в raw train, календарных границ, лагов и справочных дат.

Проверка повторов полных строк и общих карт использует предыдущий полный проход по 64-битным отпечаткам; повторно эти отпечатки не вычислялись. Они являются практической проверкой, а не доказательством отсутствия хеш-коллизий.

В проекте найдены аналитические скрипты и frontend, который по собственному README использует синтетические демонстрационные значения и не обучает модель. Поиск и чтение этих файлов не выявили ML-обучения или backtesting. Поэтому для лагов, преобразований и справочников описаны проверенные условия возникновения утечки, а не приписанные несуществующей модели дефекты.

Результаты: `temporal_split_audit.json`, `temporal_availability_scan.json`, `test_labels_exposed_in_raw_train.csv`. Воспроизведение: `python analysis/dataset/audit_temporal_split.py`; нужны pandas, NumPy, openpyxl и `rg`. Режим `--reuse-scan` повторяет малые проверки, используя уже сохранённый проход; размер и время модификации исходных CSV проверяются перед повторным использованием. Точное совпадение загрузок с границами дополнительно проверяется поиском строк и разбором соответствующего CSV-поля.

Изменять исходные CSV для устранения этих проблем не требуется. Нужны календарное разделение, полная сетка и контроль доступности данных и признаков.
